# 第03章｜消息 Key 与顺序性：同一订单的事件如何排队

## 顺序要求要先说清楚范围

订单 `O1001` 先创建再支付，积分消费者不希望先看到支付再看到创建。另一个订单 `O1002` 与它通常没有严格先后关系。真正需要保护的是“同一订单的事件顺序”，而不是让全站所有订单都挤进一个队列。

Kafka 的 Key 可以承载这个业务对象标识。本系列选择 `order_id` 作为 Key，Value 保存事件 JSON，`event_id` 标识某一次具体事件。每条事件都用不同 `event_id` 做 Key，反而无法把一个订单的多条事件稳定归到一起。

## 核心机制：Key 帮助选分区，顺序落在分区内

在没有显式指定分区、没有自定义分区器、未忽略 Key 等条件下，Java Producer 根据序列化后的 Key 选择分区。**分区数量、分区策略和 Key 的序列化方式保持一致时**，相同 Key 可以保持同一落点。Key 字符串相同但编码不同，也可能影响结果。[ProducerRecord API](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/producer/ProducerRecord.html)

分区保存的是追加顺序，不是自动按事件中的时间字段排序。两个独立生产者同时发送同一订单事件，Kafka 不知道哪个业务动作应先发生；消费者把记录交给并发线程处理，也可能先完成后来的记录。要达到业务顺序，发送侧、分区选择和消费侧执行方式都要配合。

## 用控制台发送相同订单的两条事件

前置条件：`kafka-learn` 已运行，`learn-kafka-orders` 已按第 02 章创建为三个分区、一个副本。生产者启用 Key 解析，以竖线分隔 Key 与 Value：

```bash
docker exec -it kafka-learn /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic learn-kafka-orders \
  --property parse.key=true --property 'key.separator=|'
```

依次输入以下两行。每一行发送一条记录，左侧 `O1001` 才是 Kafka Key；仅在 JSON 中写 `order_id` 不会自动设置 Key。

```text
O1001|{"event_id":"E1001-created","event_type":"OrderCreated","order_id":"O1001","sequence":1}
O1001|{"event_id":"E1001-paid","event_type":"order.paid","order_id":"O1001","sequence":2}
```

在另一终端查看 Key 和分区位置：

```bash
docker exec -it kafka-learn /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic learn-kafka-orders \
  --group learn-kafka-key-observer --from-beginning \
  --property print.key=true --property print.partition=true \
  --property print.offset=true
```

预期刚发送的两条 `O1001` 记录落入同一分区，创建记录的 Offset 小于支付记录。不要预先写死分区号，也不要要求 Offset 恰好相邻，其他生产者也可能插入该分区。控制台还可能显示此前章节的记录。本文未实测，输出以本地环境为准。

## 顺序会在哪些地方被打破

首先是重试。Java Producer 在关闭幂等、允许多个未确认请求并启用重试时，前一个批次失败而后一个成功，可能产生重排。Kafka 4.1.2 Java 客户端的幂等配置有相互约束，不能只记一个开关就忽略其他参数；其他语言客户端需查自身文档。[Producer 配置：幂等与在途请求](https://kafka.apache.org/41/configuration/producer-configs/)

其次是分区扩容。分区从 3 变成 6 后，Key 到分区的映射可能改变，而旧记录仍留在旧分区。消费者若同时读两个落点，同一订单前后的事件就可能交错。严格顺序业务应预先设计迁移、停写排空或应用层序列校验，不能直接认为“相同 Key 永远同分区”。[官方运维：增加分区的影响](https://kafka.apache.org/41/operations/basic-kafka-operations/)

再者是热点。若一个大商家占了大半流量，用 `merchant_id` 作 Key 可能把大量消息集中到一个分区。改用 `order_id` 有助于分散订单，但会失去商家范围的统一顺序。这是业务顺序范围与并行能力之间的选择。

`sequence` 可以帮助发现缺口和乱序，但 Kafka 不会替业务校验它。若先收到序号 3，消费者需要自行决定等待、补查还是拒绝处理，并考虑重复投递。

## 小练习

分别为“同一订单状态变化”“同一用户余额流水”“互不关联的页面点击”选择 Key，写出要保护的顺序范围。再判断：把 Key 从 `order_id` 改成 `event_id`，分区数不变，是否仍能保证同一订单落在一个分区？

本章不执行分区扩容，也不清除前面事件。练习结束以 `Ctrl+C` 退出客户端，数据供后续章节继续观察。
