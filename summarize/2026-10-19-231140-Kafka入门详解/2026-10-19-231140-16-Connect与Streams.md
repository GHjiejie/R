# 第16章｜Connect 与 Streams：搬运数据和计算数据怎样分工

**本章问题：数据库变更要进 Kafka，支付金额又要实时汇总，是否都得手写 Consumer？**

两项需求都围绕事件，但职责不同。Kafka Connect 为持续的数据接入、输出提供框架；Kafka Streams 是编写流处理应用的 Java 库。它们都需要部署、配置和观察，安装 Broker 不会自动获得所有数据库适配器或一个 SQL 查询服务。

本章以 Kafka 4.1.2、KRaft 为教学基线。这里提供职责说明和伪代码，没有创建或运行 Connect、Streams Demo。

## Connect：框架负责运行，Connector 负责适配

Source Connector 把外部系统数据带进 Kafka；Sink Connector 将 Kafka 记录写入外部系统。Worker 执行连接器的 Task，并提供配置、状态与进度管理。独立模式适合简单学习，分布式模式支持在 Worker 间分配任务，但外部系统仍可能是吞吐瓶颈。[Connect 用户指南](https://kafka.apache.org/41/kafka-connect/user-guide/)

例如支付数据库的 Outbox 表产生 `event-pay-1001`，数据库 CDC 连接器捕获已提交变化，再由转换规则生成以 `order-1001` 为 Key 的支付事件。连接器必须另外选择和安装，并确认数据库日志、权限、版本与快照行为。不能在任意 Worker 上写一个不存在的类名就期待它正常工作。

下面只展示一段配置意图，不能单独作为可运行配置：

```json
{
  "name": "learn-kafka-paid-sink",
  "config": {
    "connector.class": "替换为已安装的 Sink Connector 类",
    "topics": "learn-kafka-orders",
    "tasks.max": "1"
  }
}
```

实际还需目标系统地址、认证、Converter、错误策略等配置。Connector 自身支持的错误与提交机制决定端到端语义，不能因为使用 Connect 就宣称外部数据库只写一次。默认失败行为与允许跳过的策略也应先核对，否则可能把有问题的支付记录悄悄隔离。

## Streams：应用代码持续处理事件

Streams 应用从输入 Topic 读取，执行过滤、转换、聚合、关联，再将结果写回 Kafka。它运行在你部署的应用进程中，业务代码和 Broker 分开发布。需要查 SQL 的工具属于另外的产品或系统，不能把 Streams 当成 Broker 内置 SQL 服务。[Kafka Streams 介绍](https://kafka.apache.org/41/streams/)

为了按商户聚合，本章在第 01 章事件上扩展 `merchant_id` 和 `occurred_at`，并明确事件版本。下面是需要由 Producer 额外发布的教学输入；此前缺少这些字段的旧事件，必须按约定隔离或补全，不能默认为某个商户，也不能把缺失金额当成零。

```json
{
  "event_id": "event-pay-1001",
  "event_type": "order.paid",
  "schema_version": 2,
  "order_id": "order-1001",
  "merchant_id": "merchant-10",
  "amount_cents": 29900,
  "occurred_at": "2026-10-19T23:11:40+08:00"
}
```

```text
教学拓扑伪代码
读取 learn-kafka-orders
只选择 event_type=order.paid 的记录
解析 event_id、order_id、merchant_id、amount_cents、occurred_at
校验格式并隔离错误记录
按 event_id 去重
选择 merchant_id 作为聚合 Key
按 occurred_at 的 1 分钟事件时间窗口汇总支付金额
写入 learn-kafka-paid-minute-total
```

输出代表窗口结果如何变化，要约定为增量事件还是最新累计值。若最新累计值依次为 1000、2500，下游不能把两条相加为 3500。`amount_cents` 使用整数分，避免货币单位和浮点运算带来歧义。

## 有状态计算还需要回答什么

窗口依据事件时间还是处理时间？晚到记录接收多久？重复的 `event-pay-1001` 怎样识别？同一事件重复但金额不同，是拒绝还是修正？这些都是业务规则，不能仅靠调用聚合 API 决定。

有状态操作可能使用本地状态存储、changelog 和 repartition Topic。应用需要可写磁盘、明确 `application.id`，恢复时还要回放相应状态。窗口大小、允许迟到时间和去重保留范围应共同设计；过短会漏去重，过长会增加状态成本。[Streams 应用配置](https://kafka.apache.org/41/streams/developer-guide/config-streams/)

`processing.guarantee=exactly_once_v2` 可协调 Streams 的 Kafka 输入位移、状态更新与输出，但不能让自定义代码中的外部 HTTP 调用随事务回滚。调用第三方扣款时，仍要使用对方支持的业务幂等与对账机制。

## Schema 与运行现象

Producer、Connect 与 Streams 都需要就字段和编码达成一致。Schema Registry 是可选的外部组件，并非 Apache Kafka Broker 内置服务；使用 JSON 也仍然需要事件版本、字段含义和兼容规则。新增可选字段通常比把 `amount_cents` 悄悄改成元更容易兼容。

预期现象：停止 Streams 应用后，Broker 仍可接收支付事件；应用恢复时，在历史和状态日志仍可用的前提下继续处理。清空状态目录、改变 `application.id` 或删除内部 Topic，可能改变恢复与重算行为，不应随手当作清理操作。

练习：把“复制 Outbox 变化”“按商户算每分钟金额”“查询某订单当前状态”分配给 Connect、Streams、业务数据库，并说明每条链路的失败如何发现。重点是选择合适职责，同时保留可验证的业务结果。
