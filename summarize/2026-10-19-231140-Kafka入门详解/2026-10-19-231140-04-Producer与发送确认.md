# 第04章｜Producer 与发送确认：发送成功究竟说明什么

## 支付事件从代码走到 Kafka，要经过几步

订单服务调用 `send()` 后，并不是消息立刻跨过网络、写入所有副本、通知积分系统。客户端通常先序列化记录，再按目标分区组织批次，通过网络发给对应分区的 Leader，最后根据配置等待确认。

因此至少要区分：应用把记录交给客户端、Broker 按约定确认写入、下游完成业务处理。这三个时刻可以相差很远。支付页面显示成功的标准，应由支付业务决定，不能用“函数调用没有立即报错”代替可靠性设计。[KafkaProducer API](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html)

## 核心机制：acks 约定等待什么确认

`acks=0` 不等待服务端确认，应用难以据此判断 Broker 是否收到；`acks=1` 等待 Leader 写入本地日志，不等待其他副本追上；`acks=all` 等待当前 ISR 中的副本确认，并受最小同步副本等条件约束。

`all` 不是 Topic 所有已配置副本在任何时刻都必须在线；更不是“每条消息已执行 fsync”，也不是“积分已到账”。Kafka 利用文件系统与页缓存，复制确认和物理介质强制刷盘是不同层面的事情。[Producer 配置：acks](https://kafka.apache.org/41/configuration/producer-configs/)、[官方设计：持久化](https://kafka.apache.org/41/design/design/)

本系列单节点 Topic 只有一个副本，设置 `acks=all` 仍然只有一份数据。不能靠一个参数把它变成生产环境的三副本容错集群。多副本、最小同步副本与故障选主将在专门章节展开。

## 用明确配置发送一条学习事件

前置条件：`kafka-learn` 已运行，`learn-kafka-orders` 已创建。以下参数属于 Kafka 4.1.2 自带的 Java 控制台生产者：

```bash
docker exec -it kafka-learn /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic learn-kafka-orders \
  --property parse.key=true --property 'key.separator=|' \
  --producer-property acks=all \
  --producer-property enable.idempotence=true
```

输入下面一行并回车：

```text
O1004|{"event_id":"E1004-paid","event_type":"order.paid","order_id":"O1004","amount_cents":8800}
```

预期订阅该 Topic 的消费者随后可以看到记录。控制台生产者通常不为每条输入打印成功提示，屏幕安静不能直接证明成功。本文未实际运行这些命令；错误应查看客户端输出并结合消费者与 Topic 状态核对。

业务代码需要观察发送结果。下面是 **Java 客户端教学片段**，省略依赖、导入、配置对象和关闭逻辑，不是可直接执行的完整程序：

```java
// props 还需 bootstrap.servers、Key/Value serializer 等配置
props.put("acks", "all");
props.put("enable.idempotence", "true");
var record = new ProducerRecord<String, String>(
    "learn-kafka-orders", "O1004", eventJson);
var metadata = producer.send(record).get();
System.out.println(metadata.partition() + ":" + metadata.offset());
```

这里逐条 `.get()` 是为了直观看到确认或异常，会限制并发吞吐。正式实现可以使用回调或组合 Future，但必须处理同步异常、异步失败与应用退出前的发送收尾。Node.js、Go、Python 库的参数命名、默认值和回调形式可能不同，不能直接照搬 Java 配置。

## 超时为什么不总能证明“没写进去”

设 Broker 已写入 `E1004-paid`，但确认包丢失，生产者可能只看到超时。此时“是否写入”对应用是不确定的。应用随手生成新的事件 ID 再发一次，可能让下游认为这是另一笔业务。

Producer 幂等功能处理特定发送重试导致的重复写入；应用主动再次调用发送、跨进程重新发布同一业务事件等情况，还需要稳定事件 ID 和业务幂等设计。它不会自动把数据库事务、Kafka 写入和下游积分事务合成一个事务。

批处理也有成本取舍。等待一小段时间积累批次可以提高吞吐，却可能增加低流量下的延迟。应根据真实消息大小、吞吐和延迟目标调整，不能直接把课堂参数当成生产最佳值。

## 小练习

对“`send()` 已返回”“Future 已成功完成”“积分数据库已提交”分别写出能确认什么。再设想确认包丢失：为什么重发时保留原 `event_id`，比生成一个新的 ID 更便于下游去重？

练习结束用 `Ctrl+C` 退出控制台，保留学习事件。不要通过停掉已有 Broker 来验证可靠性；本章单节点环境不足以演示副本故障容错。
