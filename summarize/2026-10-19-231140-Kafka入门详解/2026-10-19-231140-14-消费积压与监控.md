# 第14章｜消费积压与监控：消息还在，业务为何越来越慢

**本章问题：支付接口正常，积分却晚了半小时，应该先查什么？**

Kafka 能缓冲支付事件，不能凭空增加积分数据库的处理能力。事件 `event-pay-1001` 已写入，只说明下游有机会读取；业务延迟还包含等待消费、处理、重试和提交等时间。本章采用 Kafka 4.1.2、KRaft 教学基线，所有数值和输出均为预期示意，未实际启动集群。

## Lag 是位置差，不是完整业务账单

消费组记录每个分区下一次恢复读取的位置。便于入门的示意公式是：`lag = 分区末端位移 - 已提交位移`。若末端为 150、已提交为 100，差为 50；若处理已完成但尚未提交，差值仍会包含这些位置。[消费组管理命令](https://kafka.apache.org/41/operations/basic-kafka-operations/)

不要把 50 直接当成“还有 50 个订单”。日志压缩可能留下位移空洞，事务控制记录和事务可见性也影响解释；在 `read_committed` 下，未结束事务可能使读取停在稳定位置之前。工具使用的末端口径与客户端当前位置也要辨认。[事务读取与位移 API](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)

另外，一条消息可能包含多个业务项，重复事件又可能代表同一个订单。真正的业务账单还要核对支付订单、已发积分和隔离待处理事件。

## 用独立学习消费组观察进度

前置条件是已有学习容器与 `learn-kafka-orders` Topic，并且 `learn-kafka-points` 组已经消费且提交过位移。以下是只读检查命令，不会替你启动环境：

```bash
docker exec kafka-learn /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --group learn-kafka-points --describe
```

预期示意字段如下；新组没有提交记录时，可能不存在或出现空值，不能套用数字：

```text
TOPIC                   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
learn-kafka-orders   0          100             150             50
learn-kafka-orders   1          200             200              0
```

如果只有分区 0 持续增长，先检查它是否承载热点订单 Key、慢记录或单个异常处理路径。只看全部分区总和，会掩盖一个持续落后的分区。

## 同时观察数量、时间和处理能力

| 观察项 | 它帮助回答的问题 |
| --- | --- |
| 各分区 lag 及增长速度 | 落后集中在哪里，是否越积越多 |
| 最旧待处理事件年龄 | 用户已经等待多久 |
| 业务成功、失败、DLQ 数量 | 消费推进是否转化为业务结果 |
| 处理耗时与数据库等待 | 处理时间耗在哪里 |
| 重平衡次数与发送错误 | 进度是否反复中断 |
| Broker 磁盘、ISR 与请求延迟 | 集群是否存在容量或副本问题 |

Kafka 的 JMX 指标包括请求延迟、复制状态以及客户端消费指标，实际需要采集与告警系统展示。单节点单副本学习环境不能验证多副本故障恢复。[官方监控指标](https://kafka.apache.org/41/operations/monitoring/)

教学假设：每秒新增 100 条，消费者每秒成功处理 80 条，10 分钟新增约 12000 条积压；若改进到每秒处理 140 条，净消化速度为每秒 40 条，清空需约 300 秒。该估算忽略重试、负载波动与位移口径，仅用于判断容量方向。

## 排查顺序与恢复边界

先确认消费组是否存活、分区是否分配，再看失败日志和下游耗时。若数据库连接池已满，直接增加消费者可能使等待更严重；若只有三个分区，传统消费组增加到十个实例，也不会让同一分区由十个实例同时消费。批量写入、修复慢查询或调整 Key 分布，都应对准实际瓶颈。

为了压低 lag 而提前提交位移，会把未完成业务藏起来。重置到最新位移同样是主动跳过历史，不能作为普通的恢复方法。恢复方案应注明遗漏范围、补偿来源和审批责任。

保留策略也不会因为消费者落后而无限等待。删除策略下，旧日志达到时间或大小条件后可能被清理，待消费记录因此超出可读取范围。需要把最旧事件年龄与保留窗口共同告警，并事先设计归档与业务补偿。Kafka 有积压并不等于它能永久兜底。

练习：假设 `event-pay-1001` 已隔离，其他记录全部消费，lag 降为 0。页面能否显示“全部订单积分到账”？预期答案是否定的：还要核对 DLQ、业务成功率和最终到账记录。再计算输入速度翻倍后，当前处理能力能维持多久的恢复窗口。
