# Redis 加锁的目的

Redis 分布式锁的目的是协调多个进程或服务器对同一资源的并发操作，让竞争者在锁有效期间按约定取得执行资格，减少数据冲突和重复工作。

Redis 作为多个实例都能访问的协调点保存锁状态。被保护的资源可以是缓存、数据库中的一条业务记录，也可以是一段任务处理流程。

本文补充 [Redis 分布式锁详解](./2026-11-16-154647-Redis分布式锁.md)，重点解释为什么需要加锁。

## 一、不加锁可能出现什么问题

假设商品只剩 1 件库存，应用采用“读取库存 → 判断是否有货 → 写回库存 → 创建订单”的多步流程，而且没有数据库条件更新等并发保护：

| 顺序 | 请求 A | 请求 B |
| --- | --- | --- |
| 1 | 读到库存为 1 | |
| 2 | | 也读到库存为 1 |
| 3 | 判断有货，把库存写成 0，创建订单 A | |
| 4 | | 根据之前读到的 1，把库存写成 0，创建订单 B |

最终只有 1 件商品，却创建了两个订单。问题出在两个请求交叉执行了同一段需要保持业务约束的代码，这段代码称为临界区。

加锁的目标是让这段流程有序执行：A 获得锁后检查和修改库存；B 暂时等待，获得锁后重新读取库存，此时已经是 0，就不再创建订单。

这个例子用来说明并发冲突。实际库存扣减还应由数据库条件更新、事务等机制保证正确性，尤其要处理锁过期、进程异常等情况。

## 二、为什么多个服务实例需要共享锁

部署多个应用实例后，每个进程的内存相互独立。A 进程创建的 `threading.Lock` 无法直接约束 B 进程。

所有实例都访问 Redis 中同一个锁 Key，就能竞争同一项资源的处理资格：

```redis
SET lock:product:1001 unique-token NX EX 30
```

- 同一商品使用同一个锁 Key，让请求竞争同一把锁。
- 不同商品可以使用不同 Key，避免无关请求相互等待。
- `NX` 表示只有 Key 不存在时才创建成功。
- `EX 30` 设置 30 秒有效期，避免进程崩溃后留下永久锁。
- `unique-token` 代表本次加锁，解锁时需要原子校验 token。

命令成功只代表本次取得了有期限的资格。参与者都要遵守加锁协议，才能协调临界区访问。[SET 命令说明](https://redis.io/docs/latest/commands/set/)

## 三、常见使用目的

| 场景 | 加锁想解决的问题 | 配套要求 |
| --- | --- | --- |
| 热点缓存重建 | 避免缓存过期后，大量请求同时查询数据库并回填相同数据 | 获得锁后再次检查缓存，其他请求等待、退避重试或读取允许使用的旧值 |
| 多实例定时任务 | 减少多个实例同时执行同一份任务 | 根据任务批次设计锁 Key，并持久记录完成状态或保证任务幂等 |
| 同一业务资源的多步处理 | 减少并发修改、重复计算或相互覆盖 | 重新读取业务状态，结合数据库约束保证最终结果 |

例如，一份热门缓存失效后有 100 个并发请求到达。应用可以让获得锁的请求再次检查缓存，仍然缺失时才查询数据库并回填；其他请求稍后读取已重建的缓存，从而减少重复回源。

“获得锁后再次检查缓存”很关键：等待者后来拿到锁时，缓存可能已经被前一个请求重建，通常无需再次查数据库。

## 四、Redis 命令原子，为什么还可能需要锁

Redis 单条命令的原子性只覆盖该命令本身。应用里的“先读取、再判断、再更新”包含多个步骤，它们之间仍然可能插入其他请求的操作。

例如，单次 `INCR counter` 已能完成原子的计数递增，通常无需再为这个递增单独加锁。若需要保护多个步骤共同形成的业务约束，则应评估 Lua、数据库事务、条件更新或分布式锁等机制。

选择机制时，应看被保护的状态在哪里、需要保证哪些操作一起成立。Redis 中的 Lua 脚本只能原子执行 Redis 内部操作，不能把外部数据库调用也包含进同一个事务。[Redis Lua 脚本说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)

## 五、结合本项目 Demo 理解

[demo-redis-lock/distributed_lock.py](../../demo-redis-lock/distributed_lock.py) 中，每个 Worker 都尝试获得同一把锁：

1. 获得锁后进入临界区，用 `time.sleep(hold_seconds)` 模拟业务处理。
2. 没获得锁的 Worker 在限定时间内重试。
3. 临界区结束后，使用 Lua 校验 token 并释放锁。

观察输出时，重点看“当前并发数”和“临界区重叠次数”：正常 TTL 足够时，预期当前并发数为 `1`，重叠次数为 `0`。这展示了多个进程围绕同一临界区进行协调的效果。

运行方法、预期输出和清理方式见 [Demo README](../../demo-redis-lock/README.md)。

## 六、加锁还需要配合哪些约束

- 锁过期不会自动终止旧进程的业务代码，TTL 过短可能导致临界区重叠。
- 锁释放后，重复请求仍可能再次获得锁；需要业务状态检查和幂等记录，避免重复产生副作用。
- 数据库事务、唯一约束、条件更新等机制负责保护对应数据的业务约束。
- 严格场景还要考虑故障切换和旧持有者继续写入的问题，必要时让下游校验 fencing token。

这些边界决定了锁能协调什么、业务层还要约束什么。详细机制见 [已有分布式锁总结](./2026-11-16-154647-Redis分布式锁.md) 与 [Redis 官方分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。
