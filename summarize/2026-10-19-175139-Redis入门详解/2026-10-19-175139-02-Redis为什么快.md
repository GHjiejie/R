**第02章｜Redis 为什么快**

**先把“快”说清楚**

讨论 Redis 快之前，先确定我们在测什么。服务器处理一条命令的时间、应用等待 Redis 响应的时间、商品接口的总耗时，以及浏览器把页面画出来的时间，是几件相关但不同的事。

商品详情接口可能还要读取图片、计算促销、校验权限。即使 Redis 查询很快，其他步骤仍可能很慢。因此，使用 Redis 的目标应是减少某一部分重复工作，并用指标确认整体收益。

**第一层原因：数据主要在内存里访问**

在本系列的常见部署中，Redis 主要从内存提供数据。内存适合快速随机访问，许多操作不必等待一次磁盘读取。这是低延迟的重要基础。

不过，不能据此写成“数据库每次读磁盘，Redis 每次读内存”。关系数据库也有缓冲池、索引和查询优化。即使数据库已经从内存拿到资料，执行查询、组织结果、管理并发连接，仍然需要工作。缓存能够直接复用某个业务结果，收益有时就来自减少这些重复处理。

磁盘也没有彻底退出 Redis 的工作过程。持久化、后台保存以及操作系统行为，都可能影响服务表现。知道它主要服务于内存访问，有助于理解性能方向；把它想成永远不接触磁盘，则会漏掉真实的延迟来源。[Redis FAQ](https://redis.io/docs/latest/develop/get-started/faq/)

**第二层原因：数据结构匹配操作**

用商品 Key 读取一个 String，和扫描一个含有几十万元素的集合，工作量不同。Redis 提供对应的数据结构和命令，应用可以把操作交给服务端完成，减少无意义的读取和计算。

比如，只判断商品有没有某个标签，Set 的成员判断比先取回所有标签再在应用中遍历更直接。需要前十名商品，就按范围读取排行榜，没有必要把整个榜单传回应用重新排序。

命令文档里的时间复杂度，描述数据规模增长时，主要计算量怎样变化。`O(1)` 不代表固定一微秒，也不代表传输多大的 Value 都一样快；`O(N)` 则提醒你注意元素数量。商品详情只有几百字，和一个数十兆字节的字符串，虽然都能使用 `GET`，网络传输和客户端解析成本却完全不同。[GET 命令说明](https://redis.io/docs/latest/commands/get/)、[SMEMBERS 命令说明](https://redis.io/docs/latest/commands/smembers/)

**第三层原因：高效地处理连接和命令**

Redis 的网络事件处理机制，使它能够管理许多客户端连接。常见命令执行路径主要按顺序处理请求，同时部分网络和后台工作可以使用其他线程。具体实现会随版本和配置演进，不能把整个 Redis 进程理解成永远只有一个线程。

顺序执行减少了某些并发协调开销，也意味着耗时操作可能拖慢其他请求。如果某条命令需要处理大量数据，其他连接不一定能完全避开它的影响。因此，“单线程所以一定快”不是完整解释，“使用多线程就一定更快”也同样过于简单。[Redis 延迟诊断说明](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)

对初学者更实用的判断是：每次请求有没有做过多工作，是否读取过大结果，是否把一次可以直接完成的操作拆成许多往返。

**网络往返可能比命令执行更显眼**

假设一次网络往返需要两毫秒，服务端处理一个小请求需要更短的时间。连续发送二十条命令，并且每条都等回复再发下一条，光网络往返就可能累计约四十毫秒。这只是解释关系的假设数字，不是 Redis 的典型性能承诺。

如果这些命令彼此独立，客户端可以使用 pipelining，把多个请求连续发送，再集中读取响应，减少逐条等待的开销。它改变的是通信方式，不会让命令自动成为事务，也不会把本来很重的计算变成零成本。批次过大，还会增加排队和响应缓冲压力。[Redis pipelining](https://redis.io/docs/latest/develop/using-commands/pipelining/)

回到商品业务：页面要展示十个商品时，可以先评估适合的批量读取方式，而不是在循环里制造十次串行等待。实际收益仍取决于客户端、数据类型、拓扑和数据大小，不能机械地把所有请求都塞进无限大的批次。

**同样是缓存命中，结果大小也会影响体验**

假设缓存里保存了一件商品的名称、价格和几段介绍，应用很快就能取回并解析。后来有人把该商品的全部评论也放进去，结果增长到几兆字节。此时即使命中，传输、JSON 解析和内存分配也可能拖慢接口。

缓存命中率很高，并不自动代表接口很好。命中的是怎样的数据、每次返回多少、应用拿到以后还要做什么，都会影响体验。减少不必要字段、分页读取大集合、避免反复序列化，有时比单纯增加 Redis 实例更值得先检查。

缓存未命中时，还可能同时发生 Redis 查询、数据库查询和缓存写入。如果大部分数据只访问一次，这条路径甚至增加了工作。评估时应分开看命中和未命中的请求。

**怎样观察，不靠感觉猜测**

先在相近条件下记录商品接口的请求量、响应时间分布、数据库查询量和缓存命中情况。平均值可能掩盖少数很慢的请求，可以同时关注较高百分位的延迟。不要拿空闲时的 Redis 和满负载时的数据库直接比较，再把差异全部归因于缓存。

在有权限的学习环境，可以只读查看 `INFO commandstats`、`INFO stats`，以及 `SLOWLOG GET 10`。慢日志记录的是命令执行时间，不包含客户端通信等全部开销；没有慢日志，并不能证明网络和应用没有问题。也不要为了练习去修改共享环境的记录阈值。[SLOWLOG 官方说明](https://redis.io/docs/latest/commands/slowlog-get/)

还要区分“应用没有找到有用缓存”和服务端的 Key 命中统计。应用可能读到了格式无效、业务不接受的资料；服务器看见 Key 存在，应用却仍然需要回源。这两层指标不能永远当成同一个数字。

**用商品接口做一个分析练习**

准备三种假设现象：命中率高但响应慢、命中率低且数据库忙、Redis 服务端耗时低但应用等待长。分别写出你最先检查的两个原因。第一种可以先看结果大小和后续处理；第二种检查数据是否值得复用、期限是否合适；第三种检查网络、连接池和应用排队。

本章不需要写入数据，也没有清理操作。继续学习命令时，可以始终保留这个习惯：先看操作量、往返次数和返回大小，再讨论某个组件是否“足够快”。
