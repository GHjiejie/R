**第14章｜AOF：记录写操作，帮助恢复数据**

**从快照之间的空档开始**

RDB 记录某个时间点的数据状态。假设商品 1001 的快照价格是 299 元，几分钟后缓存更新为 279 元，随后发生故障；如果只能使用旧快照，就可能恢复到之前的状态。我们自然会继续问：能不能把快照之后发生的修改也记录下来？

AOF 是 Redis 的另一种持久化方式，全称 Append Only File。它把能够重建数据修改结果的记录追加保存，启动时利用可用记录恢复状态。可以把它理解为操作记录本：先写入商品，再修改价格，后来删除缓存；恢复时，需要得到与这些有效操作相符的结果。这本记录的目标是重建 Redis 数据，而不是替业务数据库决定商品事实。官方 [Redis 持久化文档](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/) 解释了追加记录与恢复的关系。

**执行成功、写进文件、同步完成是不同阶段**

先理解一个经常被“落盘”二字掩盖的区别。商品写入 Redis 内存，应用可以立即用读命令看到它；相关记录写入 AOF 后，也可能暂时只到达操作系统的文件缓存。此时进程退出与整台机器掉电的后果未必相同：操作系统仍在时，文件缓存可能还在；掉电时，尚未可靠保存的内容就面临丢失风险。

`fsync` 用来要求操作系统把文件修改同步到持久存储。同步完成具有比单纯写入缓冲区更强的耐久意义，但实际保障仍依赖操作系统、文件系统和存储设备正确工作。学习 AOF 时，不能把客户端拿到成功响应，直接等同为任何故障下都能恢复这次修改。

```mermaid
flowchart LR
    A[修改 Redis 内存] --> B[形成 AOF 追加记录]
    B --> C[写入操作系统文件缓存]
    C --> D[按策略进行 fsync]
    D --> E[持久存储完成同步]
```

这个图表达数据经过的层次，不表示所有策略都要等到最后一步，才向客户端返回成功。确认与同步之间的关系，正是下面三种策略需要权衡的地方。

**三种 fsync 策略怎样取舍**

`appendfsync always` 更频繁地同步 AOF，确认写入时更依赖相关同步完成，因此增加了对磁盘响应的依赖。它支持合并提交，多个客户端或流水线中的操作可能共用一次写入和同步；不能机械理解为每个客户端命令都单独触发一次物理磁盘动作。它适合更重视耐久性的需求，但并不是没有性能代价。

`appendfsync everysec` 通常每秒安排同步，在性能与耐久性之间取得常见折中。经常有人把它简化为“最多丢一秒数据”，这可以帮助理解正常情况下的目标窗口，却不能作为任何异常情况下的绝对承诺。后台同步可能延迟，配置组合也会改变实际行为，故障类型同样影响结果。

`appendfsync no` 表示 Redis 不按前面两种方式主动调用 `fsync` 来同步这部分记录，而把同步时机交给操作系统。它仍然会追加写文件，并不是完全不写 AOF，但数据何时可靠保存更依赖系统行为。不要把某种系统上的典型刷新间隔，当作所有机器都相同的保证。这些选项与相关注释可查阅 [Redis 官方示例配置](https://raw.githubusercontent.com/redis/redis/8.2/redis.conf)。

还有一个需要连着看的选项：`no-appendfsync-on-rewrite`。如果配置为在后台保存或重写期间跳过相应 `fsync`，那段时间的耐久行为就可能接近未主动同步的情况。只看到 `appendfsync everysec` 一行，无法完整判断故障窗口。本章仅解释选项，不建议你为学习而直接调整现有实例。

**用商品改价推演一次故障**

假设 10:00:00 已完成一次同步，里面记录着商品 1001 的 299 元缓存。10:00:00.400，应用更新缓存为 279 元；10:00:00.800，又写入了商品 1002。10:00:00.900，机器突然掉电。如果这些后续记录尚未同步，就可能无法恢复；即使客户端此前拿到成功响应，也不能据此断定它们一定存在于恢复结果中。

如果只是 Redis 进程异常退出、操作系统和文件缓存仍正常，结果可能不同。哪些字节已经写入、哪些同步真正完成，需要结合日志和存储状况判断。这个例子想建立的是观察顺序：先问最后一次可靠保存到了哪里，再问其后的修改，而不是根据墙上经过了几秒就给出确定答案。

**记录不断增加，为什么还需要重写**

再想想商品浏览计数：同一个计数从 0 加到 100，追加记录里可能出现很多次递增，但恢复当前状态只需要知道最后应当为 100。商品名称反复修改，或者已经删除的缓存，也不必永远保留所有中间步骤。AOF 重写会基于当前数据状态生成更紧凑的恢复表示，减少不必要的历史记录。

`BGREWRITEAOF` 是触发后台重写的命令名称，Redis 也支持按配置自动安排重写。本章不执行这个命令。它返回任务已启动或已安排，不代表重写已经成功结束；后台任务已有其他持久化工作时，还会受到调度约束。参见 [BGREWRITEAOF 官方说明](https://redis.io/docs/latest/commands/bgrewriteaof/)。

重写不是把旧文件简单压缩一下，也不要求重放全部历史才能知道当前商品。它可以利用当前内存状态构造新的基础数据，同时继续记录新发生的修改。重写仍可能涉及 `fork`、写时复制和磁盘 I/O，不能认为后台任务没有资源成本。这部分成本与 RDB 一章介绍的机制有关。

**Redis 7 起，AOF 可能是一组文件**

在 Redis 7.0 及之后的多段 AOF 机制里，需要理解基础文件、增量文件和 manifest 三种角色。基础文件描述某个状态，可以使用 RDB 或 AOF 格式；后续增量文件记录之后的变化；manifest 说明当前应使用哪些文件以及顺序。因此，看见基础文件采用二进制 RDB 格式，并不表示没有使用 AOF 持久化。

重写时，父进程打开新的增量文件继续记录写入，子进程生成新的基础文件。准备完成后，Redis 更新生效的文件清单，再清理不再使用的旧文件。这个过程的重点是让重写前后的状态与期间写入能够接续。不能只拿某个文件名里带 `.aof` 的文件，就认定它足以恢复全部数据。结构与配置项见 [官方配置中的多段 AOF 说明](https://raw.githubusercontent.com/redis/redis/8.2/redis.conf)。

这也改变了备份时的思考方式：需要保留一组彼此匹配的文件与清单，不能在文件切换过程中随手复制一个文件，就假定备份完整。真正的备份应采用适合部署版本的流程，并在独立环境验证可恢复性。本章只建立这些角色的概念，不提供操作现有数据文件的修改方案。

**恢复不等于回到正确业务状态**

AOF 的目标是恢复已经记录的 Redis 状态。如果应用把错误价格写进去，这条修改也可能被可靠保存，持久化不会自动判断它与数据库是否一致。如果错误删除也被记录下来，重启通常不会凭空找回被删除的数据。把 AOF 当作能够随时撤销业务错误的保险箱，会误解它的用途。

它也不能直接充当完整审计日志。重写可能合并或移除中间操作，记录不一定包含操作者和业务理由，多段文件还可能含有二进制基础数据。要回答“谁在什么时间批准商品改价”，应由业务审计系统保存相应事实，而不是事后依赖当前 AOF 推断全部过程。

尾部写入不完整和文件中间损坏，也属于不同的恢复情况。Redis 的实际启动行为受版本和 `aof-load-truncated` 等配置影响，不能承诺任何损坏文件都能无损加载。文件修复可能丢弃数据，需先保留原始资料并判断故障。本章不会执行修复、删除或重启操作。

**只读观察与短练习**

有访问权限时，可以读取 `INFO persistence`，观察 `aof_enabled`、`aof_last_write_status`、`aof_rewrite_in_progress` 和 `aof_last_bgrewrite_status`。启用 AOF 时，还可能看到 `aof_current_size`、`aof_base_size`、`aof_pending_bio_fsync` 与 `aof_delayed_fsync` 等字段。字段随版本和状态变化，含义见 [INFO 官方参考](https://redis.io/docs/latest/commands/info/)。同步延迟计数说明需要进一步调查，不能单凭它计算已经丢失了多少条商品记录。

也可以用只读查询 `CONFIG GET appendonly`、`CONFIG GET appendfsync` 和 `CONFIG GET no-appendfsync-on-rewrite` 了解当前设置；这些命令只读取，不开启 AOF。已有数据的实例如何切换持久化方式，需要遵守对应版本的迁移流程，不能只改配置后随意重启。

短练习：假设浏览计数递增了一万次，重写后只保留足以恢复最终计数的表示，解释为什么数据没有因此丢失，却不能再拿它逐笔审计访问。再回到掉电时间线，分别假设后续同步已经完成、尚未完成，判断哪些价格和商品可能恢复。最后回答：为什么在 Redis 7 之后，单独备份一个增量 AOF 文件通常不够？
