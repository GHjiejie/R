**第12章｜内存淘汰：缓存没过期，为什么也会消失**

**先把保存期限和容量分开**

商品 1001 的缓存设置了 300 秒有效期。过了几十秒再查，应用却发现 Key 已经不存在。很多初学者会怀疑过期命令没有生效，实际上还有另一种可能：Redis 需要腾出内存，把它淘汰了。

过期时间表达的是这份副本的有效期限，并没有为它预订一块保证存活到期的内存。就像店员手边只能放有限数量的商品资料，资料虽然还有效，也可能因为资料架装满而被移走。对可以从业务数据库重建的商品缓存，这通常是能够接受的行为；应用必须随时准备处理未命中。官方的 [内存淘汰说明](https://redis.io/docs/latest/develop/reference/eviction/) 将缓存副本可重新生成作为选择淘汰策略的基本前提。

**两个配置，各自回答一个问题**

`maxmemory` 设置 Redis 进行相关内存限制与淘汰判断时使用的预算，`maxmemory-policy` 决定达到限制后采用什么规则。前者关心可以使用多少，后者关心空间紧张时保留谁。下面只是用来阅读的教学配置片段，所有配置行都保留为注释，不需要写入你的配置，更不需要据此修改正在运行的实例。

```text
# 教学示意，只读理解，不应用到现有环境
# maxmemory 1gb
# maxmemory-policy allkeys-lru
```

这里的 1 GB 不是 Redis 进程总 RSS 的硬性上限。Redis 使用的内存还涉及管理开销、分配器行为和部分缓冲区；某些用于复制或 AOF 的缓冲内存不计入淘汰判断，后台持久化也可能引入额外内存。一次加入很多数据的命令，还可能让内存暂时明显超过预算。服务器或容器不能只按照 `maxmemory` 的数字卡死容量，必须预留合适空间。

可以把 `used_memory` 理解为 Redis 分配器统计的内存指标，把 `used_memory_rss` 理解为操作系统观察到的驻留内存指标。它们的口径不同，释放数据后，分配器也不一定立即把全部内存交回操作系统。因此，看到 RSS 没马上下降，不能直接推断淘汰没有工作。各字段的准确含义可以查看 [INFO 内存指标](https://redis.io/docs/latest/commands/info/)。

**LRU 和 LFU 怎样决定保留谁**

`allkeys-lru` 面向所有 Key，近似选择最近较少使用的对象。设想商品 A 昨天很火，今天一直没有人看；商品 B 在过去一分钟里反复被访问。按照最近使用情况，B 通常更值得留下。这里的 LRU 关注“距离上次使用过去多久”，并不直接等同于总访问次数。

`allkeys-lfu` 也面向所有 Key，但近似考虑访问频率。它维护有限大小的概率计数，并结合随时间衰减的机制，避免曾经热门的商品永久占据优势。一个偶尔刚被点开一次的冷门商品，与一段时间里持续有人访问的热门商品，在 LFU 下可能得到不同的待遇。

Redis 采用的是近似算法，并不在每次操作时完整排列所有商品，再计算一个绝对精确的淘汰名单。这样可以控制判断所需的时间和内存。学习时应把它们看成适应访问特点的选择倾向，不能保证某个指定商品在每次容量紧张时都必然留下。策略细节见 [LRU 与 LFU 官方解释](https://redis.io/docs/latest/develop/reference/eviction/)。

**allkeys 和 volatile 的范围也不同**

策略名称里的 `allkeys` 表示可以从全部 Key 中选择；`volatile` 类策略只在设置了过期时间的 Key 中选择。例如，`volatile-lru` 的候选者必须带有期限。一个没有 TTL 的 Key 不会因为这个策略而成为候选，但这不意味着同一实例中的其他容量问题就消失了。

如果采用这类受限策略，却没有足够的合适候选对象，Redis 仍可能拒绝需要更多内存的写入。给商品设置 TTL 既表达业务有效期，也会影响某些策略的候选范围，但它不会把数据库中的所有数据变成无限容量。把不可丢失的业务状态与可以淘汰的商品副本放在同一个实例里，更需要认真设计范围和资源隔离。

**noeviction 不会自动让写入成功**

`noeviction` 表示不通过自动淘汰 Key 来腾空间。达到限制后，某些需要增加内存的命令可能收到内存不足错误。读取已有数据通常仍能继续，释放数据等操作也与新增数据不同，因此不能简单概括成“内存一满，所有命令都停止”。

对商品详情服务而言，这会形成一个具体分支：数据库查询成功，应用尝试填充缓存，但 Redis 拒绝写入。当前请求可以使用数据库结果返回，后续请求却可能继续未命中。如果服务只记录读取错误、不记录缓存写入错误，就容易误以为命中率下降只是过期时间太短。处理方式应结合容量和业务选择，不能靠无限重试一条注定被拒绝的写命令解决。

**用只读信息观察，而不是先改配置**

下面列的是只读查询命令，用于已经获得访问权限的学习或诊断环境。本章没有执行这些命令，也不要求为了练习制造内存压力。托管服务或当前账号可能限制某些查询，以实际权限为准。

```text
CONFIG GET maxmemory
CONFIG GET maxmemory-policy
INFO memory
INFO stats
MEMORY USAGE learn:redis:product:1001
```

`CONFIG GET` 读取当前配置，不会把示例策略写进实例，语义见 [CONFIG GET 官方文档](https://redis.io/docs/latest/commands/config-get/)。`INFO stats` 中的 `evicted_keys` 记录淘汰数量，`expired_keys` 记录过期数量；`keyspace_hits` 和 `keyspace_misses` 可以帮助判断访问效果。它们是实例统计，通常还包含其他业务的访问，不能直接当作某一个商品接口的全部指标。

观察计数器时，更有价值的是一段时间内的增量。例如，两次记录之间 `evicted_keys` 增长了 1600，说明这段时间发生了淘汰；单独看到一个累计值很大，并不能证明现在仍有问题。重启也会影响统计连续性。淘汰增长同时命中率下降，可能提示工作集放不下，但仍要结合请求分布和应用端错误判断，不能只凭一个数字下结论。

`MEMORY USAGE` 可以估计单个 Key 的内存开销，帮助发现商品缓存是否保存了不必要的字段。它统计的不只是 JSON 文本长度，还包括相关管理开销；对集合类数据，估计也可能涉及采样。参见 [MEMORY USAGE 说明](https://redis.io/docs/latest/commands/memory-usage/)。因此，“一条 JSON 有 1 KB，所以 1 GB 能放一百万条”只能算粗略起点，不能直接作为容量承诺。

**回到商品业务，怎样取舍**

如果少数商品贡献了大多数读取，保留热门工作集往往比保存全部商品更有效。可以先减少缓存字段，把图片内容改为图片地址，明确缓存对象大小，再依据真实访问模式评估 LRU 或 LFU。缩短 TTL 会增加重新加载，扩大容量有资源成本，而更复杂的策略也需要观测支持。选择策略的目标应是减少昂贵的重复查询，同时让内存行为可预测。

短练习：商品 A 最近刚访问一次，商品 B 过去一小时持续被访问但最后一次访问稍早，请分别从 LRU 与 LFU 的角度说明谁更可能留下，并解释为什么不能预测绝对结果。再假设所有 Key 都没有期限，实例使用 `volatile-lru`，指出新增商品缓存可能遇到什么问题。最后回答：为什么 `maxmemory` 为 1 GB，不能证明操作系统看到的内存一定低于 1 GB？
