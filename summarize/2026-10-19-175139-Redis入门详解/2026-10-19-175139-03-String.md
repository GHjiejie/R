**第03章｜String：保存一份商品详情**

**先从一个具体问题开始**

商品详情接口查到了商品 1001：名称是机械键盘，价格是 299 元。接下来许多用户还会访问它，应用希望把这次查到的资料暂时放在 Redis，下次按商品编号直接取得。这里最先要解决的，是怎样保存和取回“一整份内容”。String 很适合用来完成第一次实践。

本章假设本地 Redis 已启动，端口为 6379，且你已安装 `redis-cli`。先在系统终端执行连接命令，之后的 Redis 命令都输入到它的交互窗口。本文只操作指定的学习 Key，示例结果均假设没有其他客户端同时修改它。

```bash
redis-cli -h 127.0.0.1 -p 6379
```

**String 保存的是什么**

可以把一个 String Key 想成一个贴着标签的盒子。标签是 `learn:redis:product:1001`，盒子里放的是商品资料。冒号只是方便人阅读的命名习惯，不会建立真实目录；Redis 通过整个 Key 找到它对应的值。

String 的名字容易让人以为它只能保存一句话，实际上它可以保存一段字节内容。应用常把对象转成 JSON 再存入。商品看起来有多个字段，但 Redis 的普通 String 操作把它作为一整个值处理，不会自动识别里面哪部分是价格、哪部分是名称。

这也解释了后面的读写方式：`SET` 保存完整值，`GET` 取得完整值。应用收到 JSON 后，还要反序列化，才能使用其中的字段。序列化是把应用对象变成适合存储和传输的内容；反序列化则把内容还原成应用能操作的对象。

**例子一：从没有缓存，到保存商品资料**

先清理本章 Key，让起点确定。第一条 `DEL` 返回 `0` 或 `1` 都正常，取决于它之前是否存在；后续结果以删除完成为初始条件。

```text
DEL learn:redis:product:1001
GET learn:redis:product:1001
SET learn:redis:product:1001 '{"id":1001,"name":"keyboard","price_cents":29900}'
GET learn:redis:product:1001
TYPE learn:redis:product:1001
EXISTS learn:redis:product:1001
```

第一次 `GET` 返回空结果，在默认交互界面通常显示 `(nil)`，意思是没有这个 Key。`SET` 返回 `OK` 后，再次 `GET` 就能取回商品 JSON。`TYPE` 返回 `string`，`EXISTS` 返回整数 `1`。JSON 中用 `price_cents` 表示价格的分，因此 `29900` 对应 299 元。

客户端可能给 JSON 外面加引号，或显示转义反斜杠，这属于输出展示方式。不要把终端显示出来的外层包装也当作商品字段。真正需要确认的是：读回的值与写入的内容相符。缺失值的语义可参照 [GET 官方说明](https://redis.io/docs/latest/commands/get/)。

看到空结果时，也不能直接判定“商品不存在”。它只说明 Redis 当前没有这份缓存，商品仍可能存在于业务数据库。数据是否存在于业务系统，与这个 String Key 是否存在，是两个不同的问题。

**例子二：覆盖整份内容，并区分空字符串**

假设商家调整了价格，应用准备保存一份新资料。这个例子仍使用同一个学习 Key；执行前已有商品资料也没有关系，第一条 `SET` 会覆盖它。

```text
SET learn:redis:product:1001 '{"id":1001,"name":"keyboard","price_cents":27900}'
GET learn:redis:product:1001
SET learn:redis:product:1001 ""
GET learn:redis:product:1001
EXISTS learn:redis:product:1001
```

第一次 `SET` 返回 `OK`，随后读取的是价格为 `27900` 的整份新 JSON。第二次写入空字符串也会成功，接下来的 `GET` 返回空字符串，`EXISTS` 仍返回 `1`。空字符串是一个已经保存的值；`(nil)` 才表示缺失，二者不能混用。

“覆盖整份内容”还意味着，如果新 JSON 只包含价格，原来的名称不会被自动保留。Redis 没有替你合并对象。应用若想修改其中一个字段，需要先明确使用整份重写的方案，还是采用支持字段访问的数据类型。

应用代码也应显式判断客户端返回的缺失标记，例如 Python 的 `None` 或 JavaScript 的 `null`，不要只判断真假值。否则，一份合法的空字符串就可能被当成缓存未命中。

**例子三：只在满足条件时写入**

普通 `SET` 无论原来是否存在都会写入。如果应用想表达“没有资料时才初始化”或者“只更新已有资料”，可以使用 `NX` 和 `XX`。下面再次删除 Key，避免前面的空字符串影响判断。

```text
DEL learn:redis:product:1001
SET learn:redis:product:1001 '{"id":1001,"name":"keyboard","price_cents":29900}' NX
SET learn:redis:product:1001 '{"id":1001,"name":"replacement","price_cents":100}' NX
GET learn:redis:product:1001
SET learn:redis:product:1001 '{"id":1001,"name":"keyboard","price_cents":27900}' XX
GET learn:redis:product:1001
DEL learn:redis:product:1001
SET learn:redis:product:1001 '{"id":1001,"name":"keyboard","price_cents":25900}' XX
GET learn:redis:product:1001
```

首次带 `NX` 的写入返回 `OK`；第二次因为 Key 已存在，返回空结果，读取时仍是原来的键盘资料。随后 `XX` 写入成功，价格变为 `27900`。再次删除 Key 后，`XX` 因为找不到已有 Key 而不写入，最后读取仍为空。

这些命令没有使用 `SET` 的其他返回选项，因此这里的条件写入成功返回 `OK`，条件不满足返回空结果。它们判断的是 Key 是否存在，不是在比较当前商品内容是否与数据库一致，也不是完整的业务锁方案。[SET 官方说明](https://redis.io/docs/latest/commands/set/) 给出了这些选项的准确含义。

把存在性条件写在同一条命令里，也比应用先问 `EXISTS` 再决定是否 `SET` 更直接。分开询问和写入时，另一个请求可能在两步之间改变 Key，前一步看到的状态就已经不再适用。`NX` 表达的是 Redis 执行这次写入时应检查的条件。不过，`XX` 仍然不会核对旧价格是否正好等于你先前读到的值，不要把“只更新已有 Key”理解成防止所有并发覆盖。

实际接入前，还应给缓存内容定好约定：商品编号的格式、价格单位、缺省字段和编码由谁负责。相同编号若一会儿拼成 `1001`，一会儿拼成 `001001`，就会得到不同的 Key。写入和读取遵守同一份约定，才是在同一位置寻找同一件商品。

**怎样判断自己是否适合使用 String**

如果详情接口通常一次读取整件商品，应用本来就会生成 JSON，那么 String 的写入和读取路径很直观。缓存接口响应、保存一段配置文本，也属于相近的使用方式。优点是组织简单，客户端容易处理，整份内容的边界也很清楚。

如果每次只需要一个很小的字段，而整个商品资料非常大，反复取得和解析整份 JSON 就会增加传输与处理开销。复杂对象也需要考虑字段兼容：写入端新增字段以后，读取端能否正常处理？这些问题来自数据使用方式，不能单靠选中 String 自动解决。

还有两个操作习惯值得养成。其一，使用前确认 Key 的用途；普通 `SET` 可以覆盖已有 Key，即使原来保存的是别的数据类型。其二，收到 `WRONGTYPE` 时先检查 `TYPE`，不要为了让 `GET` 成功而随意删除陌生数据。练习使用明确前缀，是为了让数据归属易于辨认。

**做一个短练习，再清理现场**

从删除学习 Key 开始，尝试先用 `XX` 写入，再用 `NX` 写入。预期第一次不创建 Key，第二次创建成功。随后用普通 `SET` 把完整商品名称改为 `keyboard-pro`，读取并确认价格字段也保留在你提交的新 JSON 中。能说明为什么价格会保留，才算理解了整份覆盖的含义。

练习结束执行下面两条命令。若 Key 存在，删除返回 `1`；若已经被你删掉，返回 `0`。随后 `GET` 应返回空结果。本章只演示 String 的存取和条件写入，缓存期限由后续专门章节处理。

```text
DEL learn:redis:product:1001
GET learn:redis:product:1001
```
