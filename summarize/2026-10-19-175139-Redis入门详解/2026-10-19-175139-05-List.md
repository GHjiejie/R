记录时间：2026-10-19 17:51:39 (Asia/Shanghai)

**第05章｜List：记录最近浏览的商品**

**先想清楚：我们要保存的是一串经历**

用户先打开商品 1001，又查看商品 1002，随后返回 1001，最后浏览商品 1003。页面上的“最近浏览”希望把最近发生的行为排在前面。这里不仅需要保存商品编号，还需要保留它们的先后关系，List 就适合表达这种连续记录。

本章把用户 42 的浏览记录放在 `learn:redis:user:42:recent-products`。Redis 已在本地启动且安装 `redis-cli` 后，先从系统终端连接。接下来的命令输入到交互窗口，结果假设没有其他客户端同时修改这个学习 Key。

```bash
redis-cli -h 127.0.0.1 -p 6379
```

**List 的顺序来自怎样放入元素**

可以把 List 想成一列商品卡片，它有左端和右端。`LPUSH` 把元素放到左端，`RPUSH` 放到右端。只要约定新浏览始终使用 `LPUSH`，左边就代表最近，往右则越来越早。这个顺序是应用通过写入方式建立的，Redis 不会自动读取商品编号中的数字来判断先后。

List 的成员可以重复。两次浏览同一商品，就可能保存两次同样的编号。这里的每个位置代表一次记录，并不要求成员唯一。如果产品要求每件商品只出现一次，就需要另外设计去重步骤，不能把“最近浏览”的界面名称当作 List 已经提供的功能。

成员本身保存商品编号就足够，展示时再根据编号取得资料。若直接把整份商品 JSON 放进列表，商品改名以后，历史记录中的资料不一定会随之变化，也会增加每条记录的体积。先保持成员含义稳定，可以让后面的读取更简单。

**例子一：把新的浏览记录放到最前面**

第一条命令只删除本章学习 Key，其返回值可能是 `0` 或 `1`。完成删除后，按下面的顺序逐条执行，模拟四次浏览。

```text
DEL learn:redis:user:42:recent-products
LPUSH learn:redis:user:42:recent-products 1001
LPUSH learn:redis:user:42:recent-products 1002
LPUSH learn:redis:user:42:recent-products 1001
LPUSH learn:redis:user:42:recent-products 1003
LLEN learn:redis:user:42:recent-products
LRANGE learn:redis:user:42:recent-products 0 -1
```

四次 `LPUSH` 分别返回整数 `1`、`2`、`3`、`4`，表示每次写入后的列表长度。`LLEN` 也返回 `4`。最后读出的顺序为 `1003`、`1001`、`1002`、`1001`，正好把最近一次浏览放在最前面，同时保留两次浏览商品 1001 的事实。

如果在一条 `LPUSH` 中写多个元素，它们也会依次从左边插入。例如在空列表执行 `LPUSH key 1001 1002`，结果左边是 1002，右边是 1001，不是参数从左到右原样排列。批量写入时，先用两三个元素核对方向，比事后发现历史顺序颠倒更容易理解。[LPUSH 官方说明](https://redis.io/docs/latest/commands/lpush/) 明确描述了这个行为。

**例子二：只展示两条，和只保留三条**

本组紧接上一组执行，起点为四个元素，依次是 `1003`、`1001`、`1002`、`1001`。先观察不同范围，再真正裁剪数据。

```text
LRANGE learn:redis:user:42:recent-products 0 1
LRANGE learn:redis:user:42:recent-products -2 -1
LLEN learn:redis:user:42:recent-products
LTRIM learn:redis:user:42:recent-products 0 2
LRANGE learn:redis:user:42:recent-products 0 -1
LLEN learn:redis:user:42:recent-products
```

第一次读取返回 `1003`、`1001`。List 索引从 `0` 开始，而且范围包含结束位置，所以 `0 1` 是两个元素，`0 2` 则是三个。负数从右端计算，`-1` 是最后一个位置，因此第二次读取返回较早的 `1002`、`1001`。[LRANGE 官方说明](https://redis.io/docs/latest/commands/lrange/) 可用于核对这些边界。

读取不会改变列表，所以第一次 `LLEN` 仍为 `4`。`LTRIM 0 2` 返回 `OK`，随后列表只剩 `1003`、`1001`、`1002`，长度变为 `3`。它的意思是保留指定范围，把范围外的元素移除，属于会修改数据的命令。展示前三条与只保存前三条，是两个不同的需求。

范围越界时，`LRANGE` 会根据实际元素返回结果，不会因为列表只有三条就要求你先查长度再读。起点已经超过列表末尾时，返回空数组。缺失的 List 也可以按空列表理解；这与 `GET` 缺失 String 返回空值的展示形式不同。

**例子三：同一商品只显示一次，需要显式处理**

继续使用上组裁剪后的三个元素。现在用户又打开商品 1001，而产品希望它移到最前面，并且只出现一次。先移除旧位置，再插入新位置，最后控制长度。

```text
LREM learn:redis:user:42:recent-products 0 1001
LPUSH learn:redis:user:42:recent-products 1001
LTRIM learn:redis:user:42:recent-products 0 2
LRANGE learn:redis:user:42:recent-products 0 -1
```

`LREM` 返回 `1`，表示移除了一个匹配元素；紧接着 `LPUSH` 返回长度 `3`。最终记录依次为 `1001`、`1003`、`1002`。这里的去重来自我们主动移除旧编号，而非 List 自动忽略重复成员。

`LREM` 的数字参数决定移除方向和数量：正数从左边查找并最多删除相应数量，负数从右边查找，`0` 表示移除所有匹配项。它返回实际删除的元素数，并不返回剩余长度。在不知道历史是否已重复的情况下，`0` 可以清理这个商品的全部旧位置。[LREM 官方说明](https://redis.io/docs/latest/commands/lrem/) 给出了完整语义。

这三步在当前单客户端练习里很好理解，但它们仍是三条命令。若多个请求同时维护同一个用户的记录，中间可能交错执行。需要严格保证去重和长度时，应把组合操作作为一个并发问题单独设计；不能仅凭每条命令都成功，就推导整个步骤不会被打断。

**List 适合哪些需求，又有哪些边界**

最近操作、固定长度的事件记录、按端点进入和取出的简单任务序列，都与 List 的使用方式接近。它的优势在于明确的顺序和两端操作。`LPOP` 从左端移除并返回元素，`RPOP` 从右端移除并返回元素；它们会消费记录，与只读的 `LRANGE` 不同。

例如把新任务从左边放入、从右边取出，可以形成先进入的先处理的顺序。不过，简单弹出只代表元素离开列表，不等于业务已处理成功；要实现可靠任务处理，还需要考虑消费者失败等条件。本章只用浏览记录理解 List，不把几个列表命令直接当作完整消息系统。

如果主要需求是反复判断某个商品是否出现过，或自动保证成员唯一，List 就不一定合适。按中间位置找元素、删除所有匹配项，也不应按端点操作的成本来理解。随着列表增长，扫描和返回大量内容的工作都会变多。

浏览记录应有合理上限。不要在每次访问时无限写入，又习惯性 `LRANGE 0 -1` 读取所有历史。对于有限的最近记录，先约定保留条数、展示条数和是否去重，比背更多命令更能决定实现是否合适。

还要确定这里的“最近”采用什么口径。本章按照命令到达并执行的先后维护列表；如果手机离线后集中补交旧浏览记录，它们后到达，也会被放在前面。Redis 不会读取成员中的商品编号来恢复真实浏览时间。对普通在线浏览，这个约定可能已经够用；若业务必须按事件发生时刻排序，就应额外保存时间，并选择符合该查询需求的方案。

**练习：判断读取与删除的差别**

在第三组完成后，列表为 `1001`、`1003`、`1002`。先预测 `LRANGE 0 0`、`LPOP`、`LLEN` 各会返回什么，再依次执行验证。预期只读范围返回 1001 但不改变数据；弹出返回 1001 并移除它，长度随后为 `2`。再用 `RPUSH` 追加 1004，确认它位于右端。

结束后执行下面的清理命令。如果还有记录，`DEL` 返回 `1`；若已经清空，返回 `0`。`LRANGE` 随后返回空数组。

```text
DEL learn:redis:user:42:recent-products
LRANGE learn:redis:user:42:recent-products 0 -1
```
