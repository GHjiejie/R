**第07章｜Sorted Set：制作商品热度排行榜**

**有了商品集合，为什么还需要分数**

首页准备展示热门商品。商品 1001 的热度是 80，1002 是 95，1003 是 90。应用不仅要知道哪些商品入榜，还要按热度从高到低取前三名，并在热度变化后查询某件商品的当前位置。Sorted Set 就是为“唯一成员加上可排序分数”提供的数据结构。

本章使用本地 Redis 和 `redis-cli`，示例中的 `ZRANGE ... REV` 与分数范围选项需要 Redis 6.2 或更高版本。先在系统终端连接，后续命令输入交互窗口。所有输出都假设没有其他客户端同时修改本章榜单。

```bash
redis-cli -h 127.0.0.1 -p 6379
```

**先分清成员、分数和排名**

本章的 Key 是 `learn:redis:products:ranking`，成员是商品编号，分数是商品热度。一个成员在集合中只能出现一次，再次写入同一编号，会更新它的分数。不同成员可以拥有相同分数，所以“唯一”约束的是成员，不是分数。

排名则是根据当前排序得到的位置。分数 95 不代表第 95 名；商品新增或其他成员分数变化，都可能改变当前位置。把这三个概念分开，才能正确理解后面的 `ZSCORE`、`ZREVRANK` 和范围读取。

Redis 会维护排序关系，但不会替应用决定热度怎么计算。浏览、收藏、下单是否计分，各占多少权重，都属于产品和业务规则。本章用简单整数演示存储与排序，不把这几个分数当作真实推荐算法。

**例子一：创建榜单，并读取前三名**

先删除本章学习 Key。`DEL` 返回 `0` 或 `1` 都可以；删除完成后，录入三个此前不存在的商品编号。

```text
DEL learn:redis:products:ranking
ZADD learn:redis:products:ranking 80 1001 95 1002 90 1003
ZCARD learn:redis:products:ranking
ZSCORE learn:redis:products:ranking 1001
ZRANGE learn:redis:products:ranking 0 2 REV WITHSCORES
```

`ZADD` 返回整数 `3`，表示新增三个成员。`ZCARD` 返回成员总数 `3`，`ZSCORE` 返回商品 1001 的分数 `80`。在默认协议和交互显示下，分数可能带引号，这是返回展示方式，含义仍然是数值分数。

最后一条按分数从高到低返回商品与分数：1002 对应 95，1003 对应 90，1001 对应 80。`REV` 控制反向读取，`WITHSCORES` 请求同时返回分数。未指定分数或字典范围模式时，`0 2` 表示排名索引从 0 到 2，包含结束位置，所以最多返回三个成员。

如果省略 `REV`，默认顺序是分数从低到高，看到的就不是通常期待的热度榜前几名。`WITHSCORES` 也不会把“前三名”变成“三个输出项”：每个成员都伴随一个分数，客户端可能展示为交替项或一组结构化结果。[ZRANGE 官方说明](https://redis.io/docs/latest/commands/zrange/) 描述了这些选项与版本要求。

**例子二：设置新分数，与在原分数上增加**

本组紧接上一组，起点分数分别为 80、95、90。先将商品 1001 的分数直接设成 99，再给商品 1003 增加 7 分。

```text
ZADD learn:redis:products:ranking 99 1001
ZINCRBY learn:redis:products:ranking 7 1003
ZSCORE learn:redis:products:ranking 1001
ZSCORE learn:redis:products:ranking 1003
ZREVRANK learn:redis:products:ranking 1003
ZRANGE learn:redis:products:ranking 0 2 REV WITHSCORES
```

`ZADD` 返回 `0`，因为商品已经存在，没有新增成员；分数更新仍然成功。`ZINCRBY` 返回更新后的分数 `97`，不是新增数量，也不是本次增量。随后两次 `ZSCORE` 分别得到 99 和 97。榜单顺序变为 1001、1003、1002，对应 99、97、95。

这两个写操作的区别很实际：如果应用已经算出最终热度是 99，可以用 `ZADD` 设置；如果本次行为只应贡献 7 分，`ZINCRBY` 直接表达增量，避免应用自己先查分再计算后写回。成员尚不存在时，它会以原分数为零的方式加入。[ZINCRBY 官方说明](https://redis.io/docs/latest/commands/zincrby/) 对缺失成员和返回新分数作出了说明。

`ZREVRANK 1003` 此时返回 `1`。排名索引从零开始，最高分位置是 `0`，所以面向用户显示“第几名”时，存在的索引通常需要加一。不存在的成员返回空结果，不会自动得到末尾名次。应用判断时也别把合法的 `0` 当成未找到。

**例子三：按分数筛选，并移除下榜商品**

继续使用上一组的状态：1001 为 99、1003 为 97、1002 为 95。现在想读取热度至少 97 的商品，而不是固定取前三名。

```text
ZRANGE learn:redis:products:ranking 97 +inf BYSCORE WITHSCORES
ZRANGE learn:redis:products:ranking +inf 97 BYSCORE REV WITHSCORES
ZREVRANK learn:redis:products:ranking 9999
ZREM learn:redis:products:ranking 1002
ZCARD learn:redis:products:ranking
```

第一条把参数解释为分数边界，返回 1003 对应 97、1001 对应 99。普通数值边界默认包含端点，`+inf` 表示正无穷。第二条同时使用 `REV`，边界顺序也要反过来写成最大值在前，结果按 1001、1003 返回。

最容易犯的错，是忽略 `BYSCORE` 带来的含义变化。不加它，数字是排名位置；加上它，数字是分数范围。97 分与第 97 个位置，显然会产生不同结果。把命令意图先用自然语言说一遍，有助于检查参数是否正确。

商品 9999 从未加入，排名查询返回空结果。`ZREM` 返回 `1`，表示实际删除一个成员，剩余总数为 `2`。删除商品的榜单成员只会影响这份排名，并不会从业务数据库删除商品，也不会顺带清理它在其他 Key 中的资料。

**Sorted Set 的适用范围与常见误解**

商品热度榜、用户积分榜、按某个数值指标排序的对象，都适合这种成员加分数的模型。需要知道某个成员当前位置，或者读取一段排名时，也能直接使用相应命令，而不必每次把所有成员读回应用再排序。

如果只要求不重复、不关心顺序，普通 Set 更直接；如果需要保留每一次浏览的发生过程，成员唯一的 Sorted Set 又不能直接替代事件列表。它保存的是同一商品当前的一份分数，重复写入不会生成多条浏览记录。

成员应尽量使用稳定标识。若把商品名称或整份 JSON 当作成员，改名后写入的内容可能被当成另一个新成员，旧成员还留在榜上。用商品编号建立身份，用其他存储取得详情，可以让榜单的含义保持清晰。

分数使用双精度浮点数，不应无条件当作任意精度的金额或小数计算器。本章采用较小整数，便于关注排序本身。相同分数的不同成员也会各占一个位置，Redis 的排序索引不会自动给出业务上的并列名次；如果产品要求并列排名，还要另外定义展示规则，本章不展开同分排序细节。

榜单很大时，应只读取需要的范围。`ZRANGE 0 -1` 会请求全部成员，不应仅因为命令简短，就把它用于每次首页访问。与此同时，榜单刷新、商品下架和评分来源仍要有应用流程负责，数据结构只处理提交给它的成员和分数。

**练习：分清三个数字的意思**

第三组结束后，榜单有 1001 的 99 分和 1003 的 97 分。添加商品 1004，分数设为 120，再查询商品 1001 的分数和降序排名。预期新增数是 `1`，商品 1001 的分数仍为 `99`，排名索引变为 `1`，界面可显示第二名。再给它增加 30 分，尝试说明为什么新的分数与新的位置会同时变化。

练习结束只删除本章榜单。Key 存在时删除返回 `1`，不存在时返回 `0`，随后 `ZCARD` 应返回 `0`。别用删除整个数据库的方式清理一次练习。

```text
DEL learn:redis:products:ranking
ZCARD learn:redis:products:ranking
```
