**第08章｜过期时间：缓存可以保存多久**

**商品缓存为什么需要期限**

商品 1001 的介绍可能几小时都不变，但它总有修改的时候。如果应用把一份资料写入缓存后再也不处理，旧内容可能长期存在。随着被访问的商品越来越多，缓存也会不断积累。

过期时间给数据设置一个有效期限。它让应用可以表达“这份副本先保留一段时间，到期后重新加载”。期限需要结合业务选择，它不会自动判断内容有没有改变，也不能替代商品更新时的缓存失效通知。

本章使用 String 演示 Key 的过期机制。操作前假设本地 Redis 已启动，在终端执行 `redis-cli -h 127.0.0.1 -p 6379`。所有返回值都是预期现象，实际剩余时间取决于执行速度。

**先看没有期限的数据**

只清理本章使用的商品 Key，再保存一份资料：

```text
DEL learn:redis:product:1001
SET learn:redis:product:1001 '{"id":1001,"name":"keyboard","price_cents":29900}'
TTL learn:redis:product:1001
```

`SET` 成功返回 `OK`。此时 `TTL` 返回 `-1`，表示 Key 存在，但没有关联过期时间。它并不承诺数据永远存在：应用仍可删除，内存淘汰策略也可能移除它。

接着给它设置十秒期限：

```text
EXPIRE learn:redis:product:1001 10
TTL learn:redis:product:1001
PTTL learn:redis:product:1001
```

Key 尚存在时，`EXPIRE` 成功返回 `1`；`TTL` 按秒返回剩余时间，`PTTL` 按毫秒返回。不要要求两个数字精确换算，因为两条命令不是在同一瞬间执行。若 Key 不存在，普通 `EXPIRE` 返回 `0`。[EXPIRE](https://redis.io/docs/latest/commands/expire/)、[PTTL](https://redis.io/docs/latest/commands/pttl/)

**读懂 TTL 的三个结果**

非负整数表示剩余秒数，`0` 可能表示剩余时间已经很短；`-1` 表示存在且没有期限；`-2` 表示 Key 不存在。这三种状态不能混在一起处理。

等待超过十秒，且没有其他操作重写这个 Key，再执行 `GET`，默认 `redis-cli` 会显示空结果 `(nil)`；`TTL` 返回 `-2`。应用此时应该按“没有缓存”处理，而不是直接判断正式商品已经不存在。[TTL](https://redis.io/docs/latest/commands/ttl/)

读取本身通常不会延长这里设置的期限。你在第九秒执行一次普通 `GET`，不会自动又获得十秒。如果业务想要“访问一次就续期”，需要明确设计相应操作，并考虑热门数据可能一直不失效的后果。

**把写入和设置期限放在同一条命令里**

实际商品缓存常用下面的形式：

```text
SET learn:redis:product:1001 '{"id":1001,"name":"keyboard","price_cents":29900}' EX 300
```

`EX 300` 表示在这条写入命令中设置三百秒期限。这样不会出现“先写入成功，应用异常退出，第二条设置期限的命令没有执行”的间隙。

这只是把 Redis 内的写入和设定期限合成一个操作，并没有把数据库读取、商品更新等其他步骤一起变成原子操作。这里的三百秒也只是示例值，不能作为所有商品业务的默认答案。[SET](https://redis.io/docs/latest/commands/set/)

**覆盖数据时，期限可能发生什么变化**

下面这个练习很容易发现一个隐藏问题。先写入带期限的缓存，再用普通 `SET` 覆盖：

```text
SET learn:redis:product:1001 "version-a" EX 300
SET learn:redis:product:1001 "version-b"
TTL learn:redis:product:1001
```

如果没有其他操作干扰，最后返回 `-1`。普通 `SET` 默认清除了旧期限。应用每次重建这类缓存时，通常应重新设置合适的有效期。

如果确实需要保留原来的期限，可以使用 Redis 6.0 起提供的 `KEEPTTL`：

```text
SET learn:redis:product:1001 "version-a" EX 300
SET learn:redis:product:1001 "version-b" KEEPTTL
TTL learn:redis:product:1001
```

在期限还没耗尽时，最后读到的仍是接近三百秒的剩余值，而不是重新获得一段完整期限。它保留的是旧期限，不是自动刷新。选择哪种行为，要先看业务想让数据从什么时候开始计算有效期。

**取消期限和删除数据是两回事**

`PERSIST` 用来取消 Key 的过期时间，不会删除 Value。对一个带期限且仍存在的 Key 执行成功时返回 `1`；没有可移除期限或 Key 不存在时返回 `0`。

```text
PERSIST learn:redis:product:1001
TTL learn:redis:product:1001
```

如果成功取消期限，后面的 `TTL` 返回 `-1`。这类操作要有明确用途，不能因为某个商品很热门，就随手取消期限而忽略改价后的旧数据问题。[PERSIST](https://redis.io/docs/latest/commands/persist/)

**到点以后，Redis 怎样处理**

Redis 结合访问时检查和主动检查处理过期 Key。一个 Key 已经过期，普通读取不会继续返回它的旧值；但这不等于到达某个毫秒时，所有相关内存都会同步、立即释放。

可以把“业务读取时是否还有效”和“后台什么时候完成物理清理”分开理解。前者决定应用能否拿到缓存，后者涉及内存管理。过期也不同于内存淘汰：前者由期限到达触发，后者处理内存压力，未过期的数据同样可能被淘汰。

还有一个反向理解：设置十分钟期限，并不保证 Key 至少保留十分钟。应用主动删除、缓存更新和内存淘汰，都可能让它提前消失。因此，看到 `TTL` 返回 `-2`，只能确定此刻不存在，不能单凭这一个结果判断消失原因。排查时还需要结合过期、淘汰指标和应用操作记录。期限是一项有效性设置，不是一份完整的存活历史。

**期限应该怎样选**

期限短，旧数据可能保留更短时间，但回源更频繁；期限长，复用机会增加，也需要更认真地处理更新失效。商品介绍、展示价格、活动状态和库存可能有不同要求，不宜因为都属于商品，就使用完全相同的期限。

即使设置五分钟期限，也不能保证“商品修改后最多五分钟绝对一致”。并发请求可能晚一些把先前读到的旧值重新写入，并从那次写入重新计时。TTL 为单次缓存写入定义有效期，不直接定义整个跨系统业务的一致性保证。

**做一个可观察的小练习**

先为学习 Key 设置十秒期限，连续读几次 `TTL`；再分别尝试普通 `SET`、`SET ... EX 10` 和 `SET ... KEEPTTL`。每次先重新初始化，让三个实验互不影响。写下哪次取消期限，哪次重设期限，哪次保留期限。

最后执行 `DEL learn:redis:product:1001` 清理。本章的重点是能解释每一次剩余时间变化，而不是记住一个固定的缓存时长。
